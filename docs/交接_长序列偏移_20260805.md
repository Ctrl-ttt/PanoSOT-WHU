## 二、核心结论（复现定位）

**三序列均非"长序列后期渐进漂移"，而是早期（<40 帧）一次性决策错误 + 恢复失败：**

1. **系统信任错误信号**——0027 的 PSR=4.22 背景响应、360VOTS 的膨胀框、0057 的可靠速度外推，都被当作可信证据
2. **方向反转检测缺失**——0057 GT 反转时 tracker 继续旧方向；现成的 `_predict_long_thin_reversal_recovery` 仅对 aspect≥1.9 目标启用，0057（aspect 1.7）不适用
3. **恢复触发与信任度脱节**——0027 帧40 重定位候选只验证自身 PSR 高，未验证与目标身份/手工锚的一致性

0027 详细因果链（来自 failure_analysis + diagnose_probe）：
- 全程深度 PSR 极低（均值 1.35 < 2.0 阈值），310/327 帧跳过深度探测，靠 NCC 手工回退维持
- 帧21：deep 提议 score=0.614 位置错(iou 0.18)，NCC 更对(0.49)，系统采信 deep → NCC 模板被污染、框膨胀
- 帧40：ncc_relocalize_due（连续 8 帧 NCC 低分）触发全局重定位，deep 在错误背景产生 PSR=4.22 候选，跨越跳变门接受 → 永久丢失

### 6.1 0057 双稳态悖论破解：确定性"模式锁定"，与源码逻辑无关

此前"HEAD=0.0729 vs HEAD+P2默认关=0.1057"的二分始终矛盾，本会话最终破解：

- **0057 存在两个确定性模式**（同一份代码，取决于编译产物状态）：

- 实测规律：**任何源码修改（哪怕仅加 1 行注释）都使 0057 从 Mode A 切到 Mode B**（修改改变字节码行号表 co_linetable）。验证：干净 HEAD 5/5 Mode A；HEAD+1 注释 3/3 Mode B；HEAD+P2 完整代码（有/无注释行）均 Mode B
- 帧级对比工具：`tools/_compare_0057_frames.py`（帧 159 为发散点）；模式判定工具：`tools/_run_mode_probe.py`

**结论：此前的 "HEAD vs HEAD+P2（0.0729 vs 0.1057）" 对比完全被模式锁定污染，作废。**

- **flow 观测质量差**：LK 点在局部窗口，目标加速离开窗口后取自背景 → 只提供背景/静止位移（东向锁定），且 deep PSR 恒 1.25-1.46 不产生高置信修正
- **强制 NCC 观测验证可行性**（诊断脚本直接调用 `_predict_with_ncc`）：帧 25-80 NCC lon 正确跟随 GT 从 +36° 到 -56°，score 稳定 0.62-0.79，帧 60 后误差仅 ~10°——**NCC 是现成可用但从未被调用的独立观测源**

### 7.2 P3 实现：NCC 全局观测仲裁（`--deep-fallback-ncc-arbitration`，默认关闭）

- **原理**（tracker.py 约 L8419-8449，`_try_handcrafted_fallback` flow-first 分支）：
  - flow 被判定可靠后、采信前，若开关开启则同时运行 `_predict_with_ncc`（ERP 全局环绕搜索）
  - NCC 分数 ≥ `deep_fallback_ncc_arbitration_min_score`（0.45）且 NCC 与 flow 位移**显著冲突**（方向相反 ≥5°，或量级差 ≥5°，`deep_fallback_ncc_arbitration_min_delta_deg`）→ 采信 NCC
  - flow 不可靠时，NCC 兜底条件从 `deep_fallback_ncc_before_color_enabled` 扩展为 `or deep_fallback_ncc_arbitration_enabled`
- 新增 config 字段 3 个（L468-477）、RuntimeStats 字段 2 个（`ncc_arbitration_attempts/accepts`）、CLI 参数（batch_evaluate.py L380-384）

### 7.4 性能代价与优化（2026-08-12 二次优化）

- **P3 初始代价**：NCC 每帧全局匹配，0057 FPS 2.44→1.03（约 -58%）
