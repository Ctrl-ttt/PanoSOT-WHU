## 三、2026-08-12（Day 2）：破解悖论 + P2 消融 + P3/P3b 实现

### 3.1 0057 双稳态"模式锁定"破解
- 同一份代码存在两个确定性模式：**Mode A=0.0729 / Mode B=0.1057**（取决于编译产物状态）
- 两模式帧 0-158 逐字节一致，**帧 159（ERP 全宽箱事件）首次发散**；两模式 ~100 帧后均已永久丢失目标，0.1057 只是丢失后的运气轨迹
- **任何源码修改（哪怕 1 行注释）都会切模式**（修改改变字节码行号表）→ 此前 "HEAD vs HEAD+P2" 对比全部作废

### 3.2 P2 重定位身份一致性校验（默认关闭）
- 原理：候选被接受前与独立手工锚 `_hand_state` 交叉验证（锚可信 + 候选远离 → 拒绝）
- **6 序列消融**：仅 0009 微正（+0.0031），0057 明显负（-0.0303），其余零影响 → **不建议启用**
- 0027 帧40 未被拦截：现有 probe gate 已先拦截前 10 次重定位，P2 gate 只评估 1 次且当时锚已不可靠

### 3.3 0057 真根因最终确认：NCC 观测全程未启用 → 速度锁定
- 帧 25-80 状态轨迹 `stateLon ≈ predictedLon`（纯速度外推），velocity 恒 +1.04°/帧东移，而 GT 帧 40-65 加速西移并尺度膨胀
- 0057 有颜色 → fallback 走 flow-first 分支：flow 可靠后 **NCC/color 全被跳过**（`ncc_before_color/color_enabled=False`），无任何独立观测能打破速度锁定

### 3.4 P3 NCC 全局观测仲裁（默认开启）
- 原理：flow 可靠后、采信前同时运行 NCC（ERP 全局环绕搜索），NCC 高分且与 flow 显著冲突 → 采信 NCC
- **6 序列消融**：0057 0.1057→**0.3829**（+0.2772，3.6×），其余 5 序列零回归（无颜色分支，仲裁不可达）
- 对照实验排除模式锁定干扰：同代码 P3 关=0.1057、P3 开=0.3829

### 3.5 P3 性能优化
- 初始代价：FPS 2.44→1.03（-58%）
- 优化 1 低 PSR gating（0057 全程低 PSR 不省开销，语义正确）+ 优化 2 **间隔采样 interval=3**：AUC 0.3880（不降反升）、FPS 1.33、NCC 调用 -61% → 设为默认
- 机理：NCC 采样帧更新锚后，跳帧期间 flow 从新锚外推，适度间隔平滑观测噪声

### 3.6 P3b deep vs NCC margin 仲裁（默认开启）
- 问题（0027 帧21）：deep 提议 margin 仅 0.12 就压过空间冲突的独立 NCC 锚（位置 iou 0.18）→ 模板污染、288 帧未恢复
- 修复：deep 需高出 NCC ≥0.20（high margin）才采信
- **消融**：0027 0.0796→0.1021（+28%，prefix100 0.239→0.335），0057 顺带 0.3880→0.3902，其余零回归

## 六、关键经验教训

1. **评测可信度优先**：任何评测前删 `__pycache__`；`+45%` 的假提升曾误导两天方向
2. **模式锁定**：同源码因编译产物存在双稳态（0057 Mode A/B），对照实验必须"同代码版本、只切开关"
3. **先排除再攻坚**：P1/P1b/P2 三条路径用消融快速证伪/证真，避免在错误方向上堆参数
4. **单序列独立进程消融**：避免 config 实例共享导致的结果污染
5. **每项改动独立开关 + 6 序列全量消融**：保证收益可归因、回归可追溯
